两个核心线程分别在循环什么？

服务器不是“收到一次请求就创建一个线程”。启动时创建一个 epoll 主线程和固定数量的 CacheService worker；它们长期循环等待事件或任务。

主线程：Epoll Reactor 循环

while (true) {
    events = poller.wait();       // epoll_wait
    for (event : events) {
        if (event.fd == eventFd)
            processCompletions(); // MySQL 完成
        else if (event.fd == listenFd)
            acceptClients();      // 接受新连接
        else {
            readAvailable();      // 读客户端请求
            writeAvailable();     // 写响应
        }
    }
}

主线程只负责网络事件、客户端状态和响应顺序，不在这里执行阻塞 MySQL 查询。

worker 线程：缓存回源循环

while (true) {
    lock(mutex);
    condition.wait(...);          // 等待任务
    if (stopping && tasks.empty())
        return;
    task = tasks.pop();

    result = repository.find(task.key); // MySQL
    task.callback(result);              // 投递完成
}

worker 没有任务时睡眠；lookupAsync 入队后 notify_one 唤醒一个 worker。

线程边界：worker 不直接操作 clients、epoll 或客户端 socket；它只查询数据库并向 CompletionQueue 投递结果。客户端响应仍由主线程完成。

一次客户端请求的完整时序

以下以 GET demo:key 为例，展示从客户端发出 RESP 字节，到客户端收到响应的每一步。

所有命令的共同路径：客户端连接 → acceptNonBlocking → epoll_wait 监听 → Socket::read → Buffer 累积 → RespParser::parse → processRequests → 命令分支 → RespEncoder → EPOLLOUT → Socket::send。只有 GET 未命中会从主线程分叉到下面的异步 MySQL 回源路径。
客户端

*2\\r\\n$3\\r\\nGET\\r\\n$8\\r\\ndemo:key\\r\\n

主线程
1epoll_waitEpollPoller::wait 发现 clientFd 可读。
2Socket::readreadAvailable 从 TCP 接收字节，Buffer::append 写入输入缓冲区。
3RespParser::parse解析 RESP；不完整就等待下一批字节，完整才生成 RespValue。
4MemoryStore::getCacheService::getLocal 查询内存；未命中后设置 pendingRequestId。
5lookupAsync任务进入 tasks_，notify_one 唤醒后台 worker；主线程回到 epoll_wait。
worker 线程
6workerLoop从 tasks_ 取出 key 和 callback。
7MySQLRepository::find从 MySQLConnectionPool 获取连接，执行预处理查询并生成 LookupResult。
8callback把 clientFd、requestId、key 和结果放入 CompletionQueue，并写 eventfd。
主线程
9processCompletionsepoll 发现 eventfd 可读，取出完成结果并校验 requestId。
10回填和编码Found 时 CacheService::set 回填 MemoryStore，再由 RespEncoder 编码。
11EPOLLOUTpoller.modify 注册可写事件，writeAvailable 调用 Socket::send。
客户端

$16\\r\\nvalue from mysql\\r\\n —— 收到最终 RESP 响应。

主线程如何做出响应？

回源完成后，主线程根据 LookupResult 的状态选择响应内容；worker 不直接发送数据。

Found：查到数据

执行 CacheService::set 回填内存，编码为 Bulk String，注册 EPOLLOUT 后发送 value。

$16\r\nvalue from mysql\r\n

NotFound：数据库也没有

不回填缓存，编码为 RESP Null Bulk String，告诉客户端这个 key 不存在。

$-1\r\n

Error：回源失败

不把异常抛到 epoll 主循环，编码为 RESP Error，连接仍可继续处理后续请求。

-ERR cache backend: ...\r\n

模块职责

每层只处理自己的问题，通过接口连接，避免网络、协议、存储和数据库逻辑互相耦合。

NETWORK

网络层

Socket、InetAddress、Buffer、EpollPoller 封装 TCP、地址、缓冲区和 epoll。

PROTOCOL

RESP 协议层

RespParser 处理半包和粘包，RespEncoder 将结果编码为 RESP2 响应。

COMMAND

命令层

CommandExecutor 负责 PING、ECHO、SET、GET、MGET、DEL、EXISTS、EXPIRE、TTL、INCR、INCRBY、DECR 和 DECRBY 等命令语义，并生成 AOF 命令。

CACHE

缓存服务层

CacheService 统一封装内存读写、同 key 回源合并、空值缓存、队列限流、TTL 抖动和数据库熔断。

STORAGE

内存存储层

MemoryStore 保存 String KV，维护 TTL、内存占用、精确 LRU 链表和超限淘汰。

DATABASE

数据库层

KeyValueRepository 定义抽象；MySQLRepository 查询；MySQLConnectionPool 复用连接。

PERSISTENCE

AOF 持久化

AofLog 追加记录修改命令，启动时重放 AOF；GET 等只读命令不会写入 AOF。

BUILD

构建与配置

CMake 通过 CACHELITE_ENABLE_MYSQL 控制 MySQL 功能，运行时从环境变量读取连接配置。

SCOPE

当前边界

当前聚焦单机 String KV；暂不包含集群、主从复制、事务、Lua、Pub/Sub 和 AOF 重写。

GET 未命中：异步 MySQL 回源

这是当前版本最有区别于普通 MiniRedis 的业务链路：数据库查询不会阻塞 epoll 主线程。

线程与事件模型

主线程和 worker 线程各自负责不同类型的工作，通过线程安全队列与 eventfd 交接。

EPOLL THREAD

主事件线程

  • 等待客户端 socket 和 eventfd
  • 读取数据、解析 RESP
  • 处理内存命中请求
  • 组织响应并发送数据
WORKER THREADS

缓存回源线程

  • 等待 condition_variable
  • 消费 CacheService::tasks_
  • 借用 MySQL 连接执行查询
  • 通过 callback 投递结果
HANDOFF

线程安全交接

  • 任务队列由 mutex 保护
  • 完成队列由 mutex 保护
  • eventfd 唤醒 epoll 主线程
  • 主线程独占客户端状态
客户端 socket --(epoll)--> 主线程 --(lookupAsync)--> tasks_ --(worker)--> MySQL
      ^                 |                                      |
      +--(EPOLLOUT)-----+ <-- eventfd <-- CompletionQueue <-----+

数据与持久化

MEMORY

MemoryStore

数据首先存在内存中。每个 key 关联 value、过期时间和 LRU 位置；超限后按 LRU 淘汰。

AOF

appendonly.aof

修改命令追加到 AOF。启动时由 AofLog::replay() 交给命令执行器重放。

MYSQL

cache_entries

MySQL 是缓存未命中的回源数据源。查询成功后只回填内存，不通过普通 SET 修改数据库。

当前的 MySQL 回源是 read-through：GET 未命中才查数据库，查到后回填内存；不是启动时全量加载，也不是每次 GET 都查 MySQL。
